# AquaBlend API Contract — Sprint 1

This document is the single source of truth for how the AquaBlend REST API is
shaped: routes, request/response DTOs, status codes, and the error format.
It replaces the Sprint 1 placeholder and is kept up to date as each feature
branch merges. The auto-generated OpenAPI page (`/openapi/v1.json` in
Development, browsable via `/swagger` or your HTTP client of choice) should
always match what is written here — if they disagree, this file needs an
update.

## Conventions

- **Base path:** all endpoints are rooted at `/api`.
- **Format:** requests and responses are JSON (`application/json`), `camelCase` properties.
- **Dates:** UTC, ISO 8601 (e.g. `2026-08-02T10:15:00Z`).
- **IDs:** integer, auto-generated by the database.
- **No API versioning yet** — Sprint 1 ships a single, unversioned contract.

## Authentication

Most endpoints will eventually require a bearer token (JWT), configured by
Member 6 on `feature/authorization`. Until that lands, endpoints are open.
Once merged:

- Send `Authorization: Bearer <token>` on protected routes.
- A missing/invalid token returns `401` using the standard error format below.
- An authenticated user without the right role returns `403`.
- Planned roles: **Admin**, **Analyst**, **Viewer** (see `docs/authentication.md` for the full permission matrix once available).

## Standard Error Format

Every error response — validation failures, not-found, auth failures, or an
unhandled exception — uses the same JSON envelope, `ApiErrorResponse`
(`DTOs/Common/ApiErrorResponse.cs`):

| Field       | Type              | Description                                                   |
|-------------|-------------------|-----------------------------------------------------------------|
| `type`      | string            | Machine-readable code, e.g. `not_found`, `validation_error`     |
| `title`     | string            | Short, human-readable summary                                   |
| `status`    | number            | HTTP status code, duplicated in the body for convenience        |
| `detail`    | string (optional) | More specific explanation of this occurrence                    |
| `instance`  | string            | The request path that produced the error                        |
| `traceId`   | string            | Correlation id — include this when reporting a bug               |
| `timestamp` | string (ISO 8601) | UTC time the error was generated                                 |
| `errors`    | array (optional)  | Present only for `validation_error`; list of `{ field, message }`|

**Example — 404 Not Found**
```json
{
  "type": "not_found",
  "title": "Resource not found",
  "status": 404,
  "detail": "Scenario with id 42 was not found.",
  "instance": "/api/scenarios/42",
  "traceId": "0HN7QК...",
  "timestamp": "2026-08-02T10:15:00Z"
}
```

**Example — 400 Validation error**
```json
{
  "type": "validation_error",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "instance": "/api/scenarios",
  "traceId": "0HN7QК...",
  "timestamp": "2026-08-02T10:15:00Z",
  "errors": [
    { "field": "Name", "message": "The Name field is required." }
  ]
}
```

Any unhandled server exception is caught by `Middleware/ExceptionMiddleware.cs`
and returned as a `500` with `type: "server_error"`. Controllers/services should
still prefer to return proper `404`/`400`/`409` results themselves — the
middleware is a safety net, not the primary error path.

### HTTP status codes used in this API

| Code | Meaning               | When it's used                                              |
|------|-----------------------|---------------------------------------------------------------|
| 200  | OK                    | Successful `GET`, or a `PUT` that returns a body               |
| 201  | Created               | Successful `POST` that creates a resource (`Location` header set) |
| 204  | No Content            | Successful `PUT`/`DELETE` with nothing to return                |
| 400  | Bad Request           | Validation failure or malformed query/body                     |
| 401  | Unauthorized          | Missing or invalid credentials                                  |
| 403  | Forbidden             | Authenticated but not permitted                                 |
| 404  | Not Found             | Resource with that id doesn't exist                             |
| 500  | Internal Server Error | Unhandled exception (caught by `ExceptionMiddleware`)           |

### Water Sources — Planned (Member 4, `feature/water-sources`)

Base route: `/api/water-sources`. Entity fields: `id`, `name`, `type`, `createdAt`, `updatedAt` (see `Entities/WaterSource.cs`).

| Method | Route                     | Body                | Success        | Failure                |
|--------|----------------------------|----------------------|----------------|--------------------------|
| GET    | `/api/water-sources`        | —                    | `200` + array  | —                        |
| GET    | `/api/water-sources/{id}`   | —                    | `200` + object | `404` if not found       |
| POST   | `/api/water-sources`        | `CreateWaterSourceDto` | `201` + object | `400` on validation error|
| PUT    | `/api/water-sources/{id}`   | `UpdateWaterSourceDto` | `204`         | `400` / `404`            |
| DELETE | `/api/water-sources/{id}`   | —                    | `204`          | `404` if not found       |

Planned request/response shapes (mirroring the Scenario DTOs below so the two
resources stay consistent):

```jsonc
// CreateWaterSourceDto (request)
{ "name": "string, required, max 100", "type": "string, required, max 100" }

// WaterSourceResponseDto (response)
{ "id": 1, "name": "River Intake A", "type": "River", "createdAt": "...", "updatedAt": null }
```

### Scenarios — Implemented (Member 5, merged from `feature/scenarios`)

Base route: `/api/scenarios`. Entity fields: `id`, `name`, `description`, `createdAt`, `updatedAt` (see `Entities/Scenario.cs`).

| Method | Route                 | Body                 | Success         | Failure             |
|--------|------------------------|-----------------------|-----------------|-----------------------|
| GET    | `/api/scenarios`       | —                     | `200` + array   | —                    |
| GET    | `/api/scenarios/{id}`  | —                     | `200` + object  | `404`                |
| POST   | `/api/scenarios`       | `CreateScenarioDto`   | `201` + object  | `400` on validation  |
| PUT    | `/api/scenarios/{id}`  | `UpdateScenarioDto`   | `204`           | `404`                |
| DELETE | `/api/scenarios/{id}`  | —                     | `204`           | `404`                |

```jsonc
// CreateScenarioDto / UpdateScenarioDto (request)
{ "name": "string, required, max 100", "description": "string, required, max 500" }

// ScenarioResponseDto (response)
{ "id": 1, "name": "Drought Baseline", "description": "...", "createdAt": "...", "updatedAt": null }
```

> Note for Member 5 / Member 8: `PUT` and `DELETE` currently return a bare
> `404` (no body) when the id doesn't exist. To match the contract above,
> return `NotFound(ApiErrorResponseFactory.NotFound(HttpContext, "..."))`
> instead of `NotFound()` — see `DTOs/Common/ApiErrorResponseFactory.cs`.

### Automatic Updates / Changes — Implemented (Member 7, `feature/change-tracking`)

**`GET /api/changes?since={ISO-8601 UTC timestamp}`**

| Success (`200`) | Failure (`400`) |
|---|---|
| `ChangesResponseDto` with `requestedSince`, `serverTimestamp`, `waterSources[]`, `scenarios[]` | Missing/invalid/non-UTC `since` parameter |

> Note for Member 7: the current `400` bodies use an ad-hoc `{ "error": "..." }`
> shape. Please switch these to `ApiErrorResponseFactory.BadRequest(HttpContext, "...")`
> so `/api/changes` matches the contract used everywhere else.

Clients are expected to poll this endpoint periodically (e.g. every 15–30s),
storing the `serverTimestamp` from the previous response and passing it back
as `since` on the next call. A future iteration may replace polling with
SignalR push notifications — out of scope for Sprint 1.
